# 维护者协作指南

贡献者阅读 [贡献指南](../CONTRIBUTING.md)，AI 阅读 [AGENTS.md](../AGENTS.md)。本页说明维护者怎样组织任务和审核代码。

## 工作流程

Issue 确认需求和负责人 → Fork 独立分支开发 → PR 提交代码 → 审核和验证 → 合并 → 统一发布。

新功能和较大修改先确认方案；小型修复和文档可直接 PR。QQ群继续用于交流，但范围调整、暂停原因和验收结果要留在 GitHub，避免群消息成为唯一记录。

外部贡献者不必获得官方仓库写权限。仅在确有共同维护需求时，再向可信维护者授权。

## 主分支保护建议

以下只是配置建议，添加文档不会自动改变 GitHub 设置。

在仓库 Settings → Rules → Rulesets 中为 main 建立规则，启用要求 PR、阻止强推和分支删除。先用测试 PR 确认规则与自动编译实际运行，再决定是否要求“Android 编译”检查通过后才能合并。

只有一名维护者时，不要贸然强制一人批准：PR 作者不能批准自己的 PR。先保留维护者手动审核，等有可信共同维护者再调整审批人数，或明确配置维护者例外。紧急修复和发布也应保留原因及验证记录。

规则配置和例外权限需要维护者单独决定；不能只靠 AGENTS.md 或贡献指南限制远端写入。

## 审核清单

- 修改范围与 Issue 或 PR 描述一致，没有混入无关功能。
- hook 安装和回调有异常保护，遵守模块总开关及读屏操作配置。
- 外部代码与数据来源、许可和署名清楚。
- 无账号、令牌、私人日志、第三方 APK 或本机配置。
- 自动检查结果可查看；编译失败原因已处理。
- 触摸、语音、焦点等修改提供真实验证记录，未测场景明确标出。
- 合并冲突和审核意见已解决；双方原有行为没有被无意覆盖。
- 使用说明、用户可见文案和兼容性记录按需同步。

审核可选择评论、要求修改或认可。重要行为尽量实机验证后合并；不能验证时应明确限制，决定是否暂缓。AI 审查辅助发现问题，最终合并由维护者决定。

一般小 PR 可采用 Squash and merge，保持主线简洁；需要独立保留的提交可保留原有历史。合并时保留贡献者和来源记录，不擅自改写为维护者原创。版本号、标签和 Release 由维护者统一处理。

## 可转发给 QQ 群的说明

各位开发者好！后续请按项目 CONTRIBUTING.md 贡献代码：新功能和较大修改先建 Issue，确认方向后认领；Fork 官方仓库，在独立分支开发；完成后提交 PR，说明修改和实际测试结果，由维护者审核合并。使用 AI 时请让它先读 AGENTS.md。QQ群继续交流，重要决定同步到 Issue 或 PR。遇到 GitHub 操作问题可以在群里提问，谢谢大家！

## 后续逐步完善

先完成一次真实的 Fork → PR → 审核演练。再根据协作人数增加标签、任务看板和目录负责人，不必一开始设置复杂权限或强制审批人数。
